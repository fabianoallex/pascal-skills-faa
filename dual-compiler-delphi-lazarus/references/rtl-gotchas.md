# RTL gotcha catalog: Delphi vs FPC

Each item below is a real case, found in one of the reference projects, with the observed symptom, the root cause, and the fix that was used. When investigating a behavior that diverges between Delphi and FPC, check the closest matching category here first — there's a good chance it's already been cataloged.

If you find a new gotcha that isn't listed here, it's worth adding it in this same format (symptom → root cause → fix), and also to the `CLAUDE.md` of the project where it was found — that's how these lists grew in the original projects.

## Threading / interop

- **`IInterface` calling convention depends on platform in FPC**: `stdcall` on Windows, `cdecl` on Unix. A COM-like interface that assumes a fixed `stdcall` breaks silently (or fails to compile) on FPC's Unix side. — [`pascal-amqp-faa`](https://github.com/fabianoallex/pascal-amqp-faa)
- **`TThread.WaitFor` is not idempotent on FPC/Unix**: calling `WaitFor` more than once triggers a second, unconditional `pthread_join`, which can hang or behave differently from Delphi (where calling it again is safe). Guard with a "have I already waited for this thread" flag if the code may call `WaitFor` more than once. — [`pascal-amqp-faa`](https://github.com/fabianoallex/pascal-amqp-faa)
- **Delphi's default RTTI only publishes `public`/`published` methods**: a test method (e.g. DUnitX's `[Test]`) declared in a `private` section compiles without error but is never discovered/run, with no warning from the framework. Symptom: "the test disappeared", a lower test count than expected. Always check `public`/`published` visibility on methods decorated with test attributes. — [`pascal-amqp-faa`](https://github.com/fabianoallex/pascal-amqp-faa)
- **`Halt` leaks managed local variables**: `Halt` doesn't normally run pending `finally`/destructor cleanup on the stack, so local strings/interfaces/dynamic arrays can leak. If the process needs to exit early cleanly, prefer signaling and letting normal flow wind down, or free things manually before `Halt`. — [`pascal-amqp-faa`](https://github.com/fabianoallex/pascal-amqp-faa)
- **`SIGPIPE` kills the process on Linux without `MSG_NOSIGNAL`**: writing to a socket whose peer already closed the connection raises `SIGPIPE`, which by default kills the whole process on Linux (unlike the more commonly-seen "silent" behavior on Windows). Use `MSG_NOSIGNAL` on the send call, or explicitly ignore `SIGPIPE` at the process level. — [`pascal-amqp-faa`](https://github.com/fabianoallex/pascal-amqp-faa)
- **`TThread.Synchronize`/`.Queue` have nothing to run on in a plain console app**: both marshal the call onto the main thread via the VCL/LCL message queue, which is only pumped by `Application.ProcessMessages`/`Application.Run` or a manual `CheckSynchronize` loop. A console app (no `Forms`/`Application` unit) has neither, so a worker thread calling `Synchronize`/`Queue` can block indefinitely or the call may simply never run — with no error raised. This is easy to reach for by instinct (e.g. to log from a worker thread) and it isn't obviously wrong until it hangs. Fix: don't route console-app cross-thread work through `Synchronize`/`Queue` at all — protect the shared resource (e.g. console output) with a `TCriticalSection` and access it directly from the worker thread instead. — [`pascal-skills-threads`](https://github.com/fabianoallex/pascal-skills-threads), `src/MultiDownloader.SyncConsole.pas`
- **On FPC, a lock around `Writeln` doesn't keep lines from different threads whole once the output is redirected: add `Flush(Output)` inside the lock.** FPC's `Output` is a threadvar, so each thread writes into its own buffer, and each buffer reaches the file or pipe when it fills (or the thread ends), not when the lock is released. Observed in a console program writing from worker threads, a pool's background thread and the main thread, every line inside one `TCriticalSection` (the pattern recommended in the item above): on Linux, with the output redirected to a file as a CI script does, a line came out as `pool: 1 open (1 id` + another thread's whole line + `le), max 3; ...`. Isolated with FPC 3.2.2 (x86_64), two threads writing 200 locked lines each, output redirected: linux, 2 broken lines without `Flush(Output)` and 0 with it; win64, 0 in both. Fix: `Writeln(...); Flush(Output);` inside the lock, so what reaches the file follows the lock's order. It looks fine in a terminal and breaks in captured logs (Docker, systemd, CI). Not measured: Delphi, and an interactive terminal on Linux. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `samples/05-pool/PoolUnderLoad.dpr` (`Say`)
- **There's no ready-made replacement for `TTask.Run`/a worker pool** — the RTL gotcha table says "use dedicated work items" but that's an instruction, not a pattern. See `references/threading-worker-pool.md` for a concrete lock-protected-queue-plus-`TThread`-workers example instead of re-deriving it per project.

## Networking / HTTP client

- **No dual-compiler HTTP client is a clean fit for every case — pick one and document the trade-off.** Indy (`TIdHTTP`) ships with Delphi but is **not enabled by default in a clean Lazarus install** (its Lazarus package has to be installed first). `TFPHTTPClient` (`fphttpclient`) is FPC-only, no Delphi equivalent. Binding directly to `wininet.dll` (`external 'wininet.dll'`) compiles and runs unmodified on both compilers with zero extra packages — Windows handles HTTPS via Schannel/the system certificate store — but restricts the project to Windows only. There's no universal answer; decide and document it the same way as the encoding decision below. — [`pascal-skills-threads`](https://github.com/fabianoallex/pascal-skills-threads), `src/MultiDownloader.Http.pas`

## Sockets / timeout

- **Delphi's `TSocket.ReceiveTimeout`/`SendTimeout` only take effect if assigned while the socket is already connected**: Delphi's implementation pushes the timeout onto the real socket inside `CreateSocket`, at a point where the handle may still be invalid — assigning the timeout before connecting has no effect. Symptom: "FPC honors the timeout correctly, but Delphi waits for the entire command (or hangs) even with a timeout configured." Fix by re-assigning the timeout *after* the socket is connected. — [`pascal-redis-faa`](https://github.com/fabianoallex/pascal-redis-faa)
- **Without `TCP_NODELAY`, Nagle's algorithm plus delayed ACK costs ~40ms per round-trip on Linux (up to 200ms on Windows outside loopback) for a small-frame request/response protocol — and testing over Windows loopback hides it completely.** A 457-test server suite dropped from 12m59s to 50s on Linux/Docker after setting `TCP_NODELAY` on every socket at connect and accept. Don't trust a fast Windows-loopback run to represent Linux or real-network behavior for latency-sensitive request/response protocols. — [`pascal-amqp-faa`](https://github.com/fabianoallex/pascal-amqp-faa)

## Files / operating system

- **`SysUtils.RenameFile` does not overwrite an existing destination on Windows** — neither on Delphi nor on FPC. If the use case needs to overwrite, call `MoveFileEx` with the `MOVEFILE_REPLACE_EXISTING` flag directly, behind `{$IFDEF <YOUR_DEFINE>_WINDOWS}`. — [`pascal-dfe-broker`](https://github.com/fabianoallex/pascal-dfe-broker), unit `src/DFe.CursorStore.Arquivo.pas`
- **`MOVEFILE_WRITE_THROUGH` doesn't exist in FPC 3.2.2's `Windows` unit** — only `MOVEFILE_REPLACE_EXISTING` is available there. If the actual use case needs write-through semantics, declare the constant manually (the Windows API's numeric value is stable) instead of assuming it's in the standard unit. — [`pascal-dfe-broker`](https://github.com/fabianoallex/pascal-dfe-broker)

## Config / parsing

- **Delphi's `TCustomIniFile.ReadBool` doesn't understand `"true"`/`"false"` as text** — Delphi's implementation delegates to `StrToIntDef`, so it only recognizes `"0"`/`"1"` (and numeric variants). FPC understands `"true"`/`"false"` as text. This is a real bug that passed 52 green tests on FPC before showing up only when running on Delphi — a good reminder that "it passed on FPC" isn't enough (see the mirrored-tests section in the main SKILL.md). Fix: write a project-specific boolean-parsing function that accepts both formats, instead of relying on `ReadBool`. — [`pascal-dfe-broker`](https://github.com/fabianoallex/pascal-dfe-broker), see `DFe.Config.LerBooleano` in `src/DFe.Config.pas`

## Memory / interfaces

- **An object constructed inline as an interface-typed argument, in a call that raises an exception, leaks one block on FPC 3.2.2** (caught via heaptrc): writing something like `Foo.Bar(TMyObject.Create)` where `Bar` raises before the interface takes ownership of the object can leave the temporary object unfreed on this FPC version. Fix: assign the object to a local variable (of the interface type) before passing it into the call, instead of constructing it inline. — [`pascal-dfe-broker`](https://github.com/fabianoallex/pascal-dfe-broker)

## Generics / RTL collections

- **`TDictionary<K,V>.Create(AComparer)` with `AComparer = nil` crashes on FPC 3.2.2, but not on Delphi.** Symptom: `EAccessViolation` in `FindBucketIndex` (`generics.dictionaries.inc`) on the first `Add`/`TryGetValue` — in `pascal-db-faa` this single cause took down 30 of 158 tests at once, all through a cache class that forwarded an optional comparer parameter (`const AComparer: IEqualityComparer<K> = nil`) straight into the dictionary constructor. Root cause: Delphi's `TDictionary` replaces a `nil` comparer with `TEqualityComparer<K>.Default`; FPC's `rtl-generics` stores the `nil` as-is and later calls `GetHashCode` on it. Fix: never forward a possibly-`nil` comparer — `if Assigned(AComparer) then FMap := TMap.Create(AComparer) else FMap := TMap.Create;`. Worth grepping for in any code that wraps a generic collection and exposes an optional comparer. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `src/PascalDb.ClockCache.pas`
- **`IEqualityComparer<T>` has a different signature, and `TEqualityComparer<T>.Construct` takes different callable types.** FPC's `rtl-generics` declares `Equals(constref ALeft, ARight: T): Boolean` and `GetHashCode(constref AValue: T): UInt32`; Delphi uses `const` and an `Integer` hash. `Construct` accepts `reference to function` closures on Delphi, but on FPC 3.2.2 only a plain function pointer or an `of object` method (no anonymous functions in the stable compiler) — so the idiomatic Delphi `TEqualityComparer<TKey>.Construct(function(const L, R: TKey): Boolean begin ... end, ...)` doesn't compile on FPC. Fix: a **named** standalone function passed to `Construct` compiles on both (Delphi accepts a named function where it expects `reference to`), with the parameter modifier and hash type under `{$IFDEF FPC}`: `function KeyHash({$IFDEF FPC}constref{$ELSE}const{$ENDIF} V: TKey): {$IFDEF FPC}UInt32{$ELSE}Integer{$ENDIF};`. `BobJenkinsHash` exists in both RTLs with the same signature. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `src/PascalDb.Optionals.pas` (`SingleKeyEquals`/`SingleKeyHash`)
- **Generics themselves are not the problem under `{$MODE DELPHI}` on FPC 3.2.2.** Generic interfaces with GUIDs (`IOptional<T> = interface ['{...}']`), classes inheriting from a specialized generic (`TOptNullString = class(TOptionalNullable<string>, ...)`), generic methods with interface constraints resolving `TypeInfo(I)`'s GUID, and `Generics.Collections` all compiled and behaved identically in `pascal-db-faa` without `generic`/`specialize` keywords. The divergences were in the *collection library's* behavior (the two items above), not in the language feature — so a project that uses generics doesn't have to switch to `{$mode objfpc}`, but should test collection edge cases (nil comparers, custom comparers) on both sides.

## Types

- **`Length()` of a dynamic array is `NativeInt` on Delphi Win64** (but `Integer`/`LongInt` on other compiler/platform combinations). Comparisons or generic calls that explicitly assume `Integer` (e.g. `Assert.AreEqual(n, Length(x))` where `n: Integer`) may fail to compile on Win64. Fix with an explicit cast: `Assert.AreEqual(n, Integer(Length(x)))`. — [`pascal-dfe-broker`](https://github.com/fabianoallex/pascal-dfe-broker)
- **`TGuid.Empty` doesn't exist on FPC 3.2.2** — it comes from Delphi's `TGuidHelper` record helper. Symptom: `identifier idents no member "Empty"`. Fix: a typed constant, which works on both: `const EMPTY_GUID: TGUID = '{00000000-0000-0000-0000-000000000000}';`. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `src/PascalDb.Optionals.pas`
- **A `Double(...)` typecast of a `Currency` converts the value on FPC for Windows but not on FPC for Linux.** Observed in a console sample that printed a price with `Format('%8.2f', [Double(Query.Currencies['PRICE'])])`: `12.50` on Windows, `125000.00` on Linux, with the same data. Isolated afterwards with the same compiler (FPC 3.2.2, x86_64) on both targets, for `C := 12.5`: on win64, `Double(C)` gives `12.50` whether `C` is a variable or a function result; on linux, it gives `0.00` for a `Currency` variable and `125000.00` for a `Currency` function result (the value's internal Int64, scaled by 10000), both printed directly and inside `Format`. No warning or hint on either target. An assignment (`D := C`, `D: Double`) gave `12.50` in every case. Fix: convert by assignment to a `Double` variable, never by typecast; a Linux run is what exposes it. Not measured: Delphi, other CPUs/targets, and FPC versions other than 3.2.2. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `samples/03-migrations/Migrations.dpr` (`ListProducts`)

## Encoding

- **Delphi's `TEncoding.UTF8.GetString` raises on byte sequences that aren't valid UTF-8; FPC doesn't.** This is harmless if the data is always text, but dangerous when the data may be binary — for example, arbitrary values stored in Redis, which have no guarantee of being valid UTF-8 text. On Delphi, a binary value received in a pub/sub callback could silently crash the application (an unhandled exception inside the callback), while FPC processed it normally. Fix: use a tolerant, project-specific encoder (e.g. based on `TMBCSEncoding`) instead of `TEncoding.UTF8` directly whenever the data isn't guaranteed to be text. — [`pascal-redis-faa`](https://github.com/fabianoallex/pascal-redis-faa)
- **FPC console/service programs silently replace characters outside the default code page with `?`.** In `{$MODE DELPHI}`, `string` is an AnsiString in the process's default code page. Measured on FPC 3.2.2/Windows: a plain console program runs with `DefaultSystemCodePage` = 1252, and UTF-8 bytes read from a resource through `TStringList.LoadFromStream(Stream, TEncoding.UTF8)` came back as `61 3F 62` for `'a→b'` (`→` is not in cp1252); after `SetMultiByteConversionCodePage(CP_UTF8)` the same code returned `61 E2 86 92 62`. An LCL program doesn't have the problem: measured `DefaultSystemCodePage` = 65001 even before `Application.Initialize` (the LCL units set it during initialization) — which is why this stays invisible while testing with an LCL test runner or GUI app. This is distinct from the console *display* issue (cp850 mojibake) and from the source-file encoding policy: here the data in memory is corrupted, whether or not anyone prints it. Fix: call `SetMultiByteConversionCodePage(CP_UTF8)` at the start of every non-LCL FPC program (console, service, test runner), and have code that decodes UTF-8 refuse non-ASCII input when `DefaultSystemCodePage <> CP_UTF8` instead of silently degrading it. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `src/PascalDb.SqlSources.pas` (`PdbUtf8BytesToString`)
- **On Unix, FPC without `cwstring` mangles non-ASCII text in WideString Variants.** Observed: a test comparing `'São Paulo'` read back from a `Variant` passed on Delphi and FPC/Windows but returned `'S�o Paulo'` on FPC 3.2.2/Linux; adding `cwstring` to the program's `uses` fixed it. Isolated afterwards on Linux, with the code page already set to UTF-8: a non-ASCII **literal passed in an `array of Variant`** becomes a `varOleStr` (a WideString), and converting it back to `string` without `cwstring` produced one byte per character (Latin-1): `'São'` = `53 C3 A3 6F` came back as `53 E3 6F`, invalid UTF-8 (hence the `�`, not a `?`). With `cwstring`: `53 C3 A3 6F`. In the same isolated test, a `string` variable stored in a `Variant` (`varString`, no conversion) and a direct `string` ↔ `WideString` assignment were **not** affected — so the scope is narrower than "every WideString conversion", but it's exactly what a mock/record layer holding values in Variants, or a database driver returning WideString fields, runs into. Fix: put `cwstring` next to `cthreads` in the `{$IFDEF UNIX}` part of every FPC program's `uses`. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `tests/Unit/fpc/PascalDbUnitTestsFpc.lpr`
- See also, in the main SKILL.md, the "Encoding and accented characters" section about the source-file encoding policy (ASCII vs UTF-8-with-BOM) itself — that's a distinct problem: it's about the `.pas` file, not about runtime data.

## Database access

- **On Delphi, `AsString` on a string query parameter makes it ANSI, and characters outside the ANSI code page reach the database as `?`.** Observed with FireDAC (Delphi 12 CE, Win32) against Firebird 2.5 with `CharacterSet=UTF8` and a `CHARACTER SET UTF8` column: `'São Paulo → ok'` written through `TFDParam.AsString` was read back as `'São Paulo ? ok'`. `ã` survives because it exists in cp1252; `→` doesn't — which is why text in Portuguese (or any language that fits the Windows code page) never shows the bug. Setting the value with `AsWideString` (a `ftWideString` parameter, and `DataType := ftWideString` before `Clear` for a NULL) fixed it: the same test passed. Reading needed no change (with a UTF-8 connection the field comes back as a Unicode string). Data.DB's `TParam.AsString` also makes an `ftString` parameter, so a wrapper over `TParams` got the same fix — not exercised against a database on Delphi. Not every driver has the problem: ZeosLib 8 has its own `TZParam`, whose `AsString` is a Unicode string on Delphi, and the same round-trip test passed through it with plain `AsString` (Delphi 12 CE, Win32, Firebird 2.5). FPC is not affected: its `string` is already UTF-8 (given the runtime code page in the "Encoding" section). — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `adapters/firedac/PascalDb.Adapter.FireDAC.pas` (`SetStringParam`), `src/PascalDb.Adapter.DataSet.pas` (`TDBParams`), `adapters/zeos/PascalDb.Adapter.Zeos.pas` (`TZeosParamsAdapter`)
- **SQLdb loads a database client library (fbclient, libpq) once per process, and the first load wins.** Observed: an integration suite passed only while the connection pool happened to connect first (loading the configured `fbclient` through a `TSQLDBLibraryLoader`); once a plain `TIBConnection` was used first to create the test database, it loaded the default `fbclient.dll` found on the search path, and every later connection failed with `Firebird interface already initialized from library fbclient.dll`. Fix: load the intended library explicitly (`TSQLDBLibraryLoader` with `ConnectionType`/`LibraryName`, `Enabled := True`) before any SQLdb connection is opened, including throwaway ones used for setup. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `adapters/sqldb/PascalDb.Adapter.SQLdb.pas` (`PdbSQLdbUseClientLibrary`)
- **On Windows, a client library loaded by full path doesn't find its own dependencies.** Observed with SQLdb (FPC 3.2.2, Win64) and the `libpq.dll` of a PostgreSQL 18 install: with the install's `bin` folder on `PATH` the suite passed; with that folder removed from `PATH`, every test failed with `Can not load PostgreSQL client library "C:\Program Files\PostgreSQL\18\bin\libpq.dll"` — the full path was right, but `libpq.dll` needs `libssl`, `libcrypto`, `libintl`, ... from the same folder, and the default DLL search order doesn't include the folder of the DLL being loaded. ZeosLib 8 passed without `PATH`: its loader calls `LoadLibraryEx(..., LOAD_WITH_ALTERED_SEARCH_PATH)` when given a path. Fix: load the library that way first (`LoadLibraryExW(path, 0, LOAD_WITH_ALTERED_SEARCH_PATH)`, keeping it loaded), so the driver's later load of the same path gets the already-loaded module; with it SQLdb passed without `PATH`, and so did FireDAC (Delphi 12 CE, Win64 — whether FireDAC alone would fail was not measured). A developer machine with the database installed usually has that folder on `PATH`, so test with it removed. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `src/PascalDb.Adapter.Base.pas` (`PdbPreloadClientLibrary`)
- **ZeosLib 8 on the Firebird 3+ API: `Commit` can loop forever after an `INSERT ... RETURNING` opened as a query.** Observed on Linux (FPC 3.2.2, Debian bookworm's Firebird 3 client `libfbclient2`, Firebird 5 server): an integration test that opens `INSERT ... RETURNING` as a query (`TZQuery.Open`, then `FetchAll`) and commits hung at 100% CPU. gdb put the main thread in `TZFirebirdTransaction.TestCachedResultsAndForceFetchAll` (`src/dbc/ZDbcFirebird.pas`): before a real commit, Zeos calls `Last` on each open cursor until the cursor removes itself from the transaction's list, and this cursor never did. The same suite had passed on Windows, where a Firebird 2.5 client makes Zeos use the legacy ISC API (`TZInterbase6Connection`), which doesn't have that code. Fix: the connection property `hard_commit=true`, which commits directly and skips the loop. With it the suite passed on Linux (Firebird 5, PostgreSQL 17) and still passed on Windows (FPC Win64, Delphi 12 CE Win32/Win64, Firebird 2.5). A hard commit invalidates cursors still open on the transaction, so read results before committing (the adapter fetches everything on `Open`). Not measured: which other statement kinds leave a cursor in that state, and Delphi against the Firebird 3+ API. Test on the client you deploy with: the Windows 2.5 client and the Linux 3+ client run different Zeos code. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `adapters/zeos/PascalDb.Adapter.Zeos.pas` (`PdbZeosNewConnection`)
- **SQLite has one writer at a time, and neither SQLdb nor ZeosLib sets a busy timeout: with a connection pool, a second writer fails at once with "database is locked".** Measured with a probe of 4 threads, each inserting in its own transaction held 200 ms, on one SQLite file (FPC 3.2.2, Linux): 3 of 4 failed within 4 ms, on SQLdb and on Zeos 8. Fix: a busy timeout on every SQLite connection — SQLdb: `PRAGMA busy_timeout = 5000` after connecting (FPC 3.2.2's `TSQLite3Connection` only handles `foreign_keys` from `Params`, and runs statements only inside a transaction, so use a throwaway `TSQLTransaction`); Zeos: the connection property `busytimeout=5000`. The probe then had 0 failures. Not measured: WAL mode, and FireDAC's own `BusyTimeout` setting. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `adapters/sqldb/PascalDb.Adapter.SQLdb.pas` (`ApplySQLiteBusyTimeout`), `adapters/zeos/PascalDb.Adapter.Zeos.pas` (`PdbZeosNewConnection`)
- **SQLdb + SQLite: "database schema has changed" on a pooled connection after another connection ran DDL.** FPC 3.2.2's `sqlite3conn` prepares with the legacy `sqlite3_prepare` (`sqlite3conn.pp`, line 262), which returns `SQLITE_SCHEMA` (17) when another connection changed the schema since this one last read it, instead of preparing again as `sqlite3_prepare_v2` does. Observed: migrations ran the DDL on one pooled connection and recorded the version on another, opened earlier, which failed with `TSQLite3Connection : database schema has changed`. Fix: on `ESQLDatabaseError` with `ErrorCode = 17` (connector `SQLite3` only), `UnPrepare` and run the statement once more — the error comes before the statement does anything, so the retry is safe; the contract suite then passed on Linux and Windows. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `adapters/sqldb/PascalDb.Adapter.SQLdb.pas` (`IsSQLiteSchemaChanged`)
- **ZeosLib 8.0.0 + SQLite stores a `Currency` parameter multiplied by 10000.** A round-trip test read `123400` for `12.34`; a probe showed the stored value was the integer `123400` for the parameter and the real `12.34` for the same literal. Cause: `TZSQLiteCAPIPreparedStatement.SetCurrency` (`src/dbc/ZDbcSqLiteStatement.pas`) binds with `sqlite3_bind_int64` over an `Int64 absolute` the Currency, i.e. its internal scaled representation. Fix: send a `Currency` to SQLite as a `Double` (convert by assignment, not a `Double(...)` cast — see "Types"); SQLite stores a `NUMERIC` with decimals as `REAL` anyway. Measured with FPC 3.2.2 on Linux; the code path doesn't depend on the compiler, but the unfixed path wasn't run on Delphi. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `adapters/zeos/PascalDb.Adapter.Zeos.pas` (`TZeosParamsAdapter.WriteCurrency`)
- **A `sqlite3.dll` built without the column-metadata functions makes SQLdb and ZeosLib crash with an access violation at address `$0`.** With Python 3.12's `DLLs\sqlite3.dll` (SQLite 3.45.3, 64-bit) as the client library, every test of both FPC 3.2.2 Windows runners (SQLdb and Zeos) failed with an AV at 0: that DLL doesn't export `sqlite3_column_table_name`, `sqlite3_column_origin_name` or `sqlite3_column_database_name` (built without `SQLITE_ENABLE_COLUMN_METADATA`), and both drivers call them through pointers that stay nil. With the official 64-bit DLL from sqlite.org (3.53.4, which exports them) both suites passed; Debian's `libsqlite3-0` has them too. Checking a candidate DLL is one line: `hasattr(ctypes.CDLL(path), 'sqlite3_column_table_name')`. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `CLAUDE.md` (gotcha 23)
- **FireDAC + SQLite in a pool needs settings changed from FireDAC's defaults: `StringFormat=Unicode`, `SharedCache=False`, and `BusyTimeout` + `UpdateOptions.LockWait = True`.** Measured with a contract suite on Delphi 12 CE (Win32 and Win64, same results), SQLite linked in through `FireDAC.Phys.SQLiteWrapper.Stat`. With FireDAC's defaults, `'São Paulo → ok'` came back as `'São Paulo ? ok'` (VARCHAR handled as ANSI, like the `AsString` item above) — `StringFormat=Unicode` fixed it. Four threads each inserting in their own transaction failed at once with "database table is locked" (a shared-cache table lock, which a busy timeout doesn't wait for); with `SharedCache=False` they still failed at once, now with "database is locked" (the whole suite took 0.29 s); with `BusyTimeout=5000` and `UpdateOptions.LockWait := True` added together, every writer waited for the lock and committed (the suite took 1.2 s). Which of those last two was needed wasn't isolated. `LockingMode=Normal` (FireDAC's documented default is `Exclusive`, which would keep a pool's other connections out of the file) was set from the documentation, never tried with `Exclusive`. The Community Edition ships no source for FireDAC's SQLite driver, so none of this came from reading it. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `adapters/firedac/PascalDb.Adapter.FireDAC.pas` (`TFDProvider.BuildConnection`)
- **SQLdb reads a backslash as an escape character when it looks for `:parameters`, on the SQLite3 and PostgreSQL connectors: with `LIKE :A ESCAPE '\'`, every parameter after it silently disappears.** Measured with FPC 3.2.2 on Linux, parameter list only (no server needed): `SELECT ... WHERE X LIKE :A ESCAPE '\' AND P >= :B AND C = :C` assigned to a `TSQLQuery` gives 1 parameter (`A`) on the `SQLite3` and `PostgreSQL` connectors — `\'` is taken as an escaped quote and the rest of the text as the inside of a string literal — and 3 on `Firebird`; with `ESCAPE '!'` all three connectors give 3. Nothing fails when the SQL is assigned: the error comes later, when binding, as `Parameter "B" not found`. Found by an agent writing a prefix search with escaped `%`/`_` against SQLite. Fix: use an escape character other than a backslash (`!`, `^`, ...), and escape that character itself in the value. Not measured: FireDAC and ZeosLib, which parse parameters with their own code. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `docs/sql.md` ("Prefix searches and `LIKE ... ESCAPE`"), `CLAUDE.md` (gotcha 26)
- **On Linux, SQLdb's default client library names don't match what the runtime packages install, for SQLite and Firebird.** Measured on Debian bookworm with only the runtime packages installed (`libsqlite3-0`, `libpq5`, `libfbclient2`), FPC 3.2.2, opening a connection with no library configured: `SQLite3` looks for `libsqlite3.so` — created only by the `-dev` package — and fails with `Can not load SQLite client library "libsqlite3.so". Check your installation.`; `Firebird` looks for `libfbclient.so.2.5.1`, `libgds.so` or `libfbembed.so.2.5` (a 2.5 client's names) and fails with bookworm's `libfbclient.so.2` (a 3.0 client); `PostgreSQL` finds `libpq.so.5` by itself. With the versioned name given (`TSQLDBLibraryLoader`, or the adapter's `ClientLibrary` setting: `libsqlite3.so.0`, `libfbclient.so.2`) both loaded. A developer machine with the `-dev` packages won't show it; a deployment image will. Three agents writing a consumer program all hit the SQLite one. Not measured: other distributions, and ZeosLib's default names. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `docs/adapters.md` ("Client libraries"), `CLAUDE.md` (gotcha 27)

## Evaluation order

- **Function-argument evaluation order is not guaranteed left-to-right** (not on Delphi, not on FPC — but this tends to surprise people who assume "like C"). A real bug appeared when building a logging call that had a side effect (e.g. incrementing a counter or consuming a value) in the middle of the argument list — the observed order differed from what the code visually suggested. Avoid relying on side effects inside argument lists; if a side effect needs to happen before a call, put it on its own line. — [`pascal-redis-faa`](https://github.com/fabianoallex/pascal-redis-faa)

## UI / cross-platform (3 axes: compiler × OS × framework)

- **Selecting a UI framework (VCL/FMX/LCL) via nested `{$IFDEF}`**, when a single compiler (Delphi) can target more than one framework:

  ```pascal
  uses
    {$IFDEF FPC}Controls, ExtCtrls, Menus,
    {$ELSE}
      {$IFDEF FRAMEWORK_FMX}
      FMX.Controls, FMX.StdCtrls, ...
      {$ELSE}
      Vcl.Controls, Vcl.StdCtrls, ...
      {$ENDIF}
    {$ENDIF}
    Classes, SysUtils, ...;
  ```

  `FRAMEWORK_FMX` is a project define (`.dproj`) chosen manually per build — not something the compiler sets on its own. — [`opcb-object-pascal-component-builder`](https://github.com/fabianoallex/opcb-object-pascal-component-builder), `src/OPCB.pas`

- **In builds targeting 3 platforms (Windows/Linux/Android), the order of platform `{$IFDEF}`s matters**: Delphi also defines `POSIX` when compiling for Android, so testing `POSIX` before `ANDROID` would misclassify an Android build as "generic Unix." The rule used: test and define the more specific case (`_ANDROID`) first, and make the generic case (`_POSIX`) explicitly exclude the case already handled. See also the equivalent note in "The compatibility `.inc` file" in the main SKILL.md. — [`pascal-pipes-faa`](https://github.com/fabianoallex/pascal-pipes-faa), `src/pipes.inc`
- Practical consequence of the Android axis: Android's `addrinfo` (bionic libc) has its fields in a different order than glibc's (`ai_canonname` before `ai_addr`) — a generic `addrinfo` struct written with Linux/glibc in mind reads the wrong fields on Android. The Android backend uses the Delphi RTL's `Posix.NetDB` instead of a generic struct for this reason.

## Resource files

- **A `.dpr` and a `.lpr` with the same program name, in the same folder, silently overwrite each other's `.res`.** `{$R *.res}` in each resolves to the identical `<program>.res` file, and both IDEs freely regenerate it on their own build (Delphi writes MAINICON/version info; Lazarus regenerates from the `.lpi`'s manifest/icon settings) — so building one compiler clobbers the resource the other one just wrote, with no warning from either side. Symptom: an icon, manifest, or version-info change made in one IDE "disappears" after building in the other. Fix: give the two program files different names (e.g. `MyApp.dpr` / `MyAppLCL.lpr`) and, if the executable name needs to stay identical, set `<Target><Filename Value="MyApp"/></Target>` in the Lazarus side's `.lpi` — the program name and the output filename don't have to match. — [`opcb-object-pascal-component-builder`](https://github.com/fabianoallex/opcb-object-pascal-component-builder) dodges this with its `no-dfm` example's `DelphiProject.dpr`/`LazarusProject.lpr` naming, though without documenting why; confirmed as a real, hit-in-practice collision building [`pascal-snake`](https://github.com/fabianoallex/pascal-snake) with this skill.
- **Loading an embedded `RCDATA` resource: `FindResource`/`TResourceStream` are portable, but `RT_RCDATA` isn't where Delphi code expects it.** On Delphi it comes from `Winapi.Windows`; on FPC 3.2.2 it's declared in the `system` unit only for non-Windows targets (`rtl/inc/resh.inc`), and on Windows it lives in FPC's own `Windows` unit — so code that drops `Winapi.Windows` for FPC gets `Identifier not found "RT_RCDATA"` on Windows. Fix: a local constant with the same value on every platform, `SQL_RESOURCE_TYPE = {$IFDEF FPC}PChar(10){$ELSE}RT_RCDATA{$ENDIF};` (`MAKEINTRESOURCE(10)`), with `Winapi.Windows` only under `{$IFNDEF FPC}`. This covers *reading* the resource. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `src/PascalDb.SqlSources.pas`
- **Producing the `.res`: a `.rc` is not portable to Linux FPC; a prebuilt `.res` is portable everywhere.** Tested with FPC 3.2.2: `{$R x.rc}` works on Windows (FPC calls the `windres` shipped with Lazarus); on Linux it fails with `resource compiler "windres" not found`, and installing the MinGW binutils (`binutils-mingw-w64-x86-64`) still fails, because that `windres` preprocesses the `.rc` with `x86_64-w64-mingw32-gcc` (from its own error message; installing the full MinGW compiler to confirm it would then work was not tested — not worth it for embedding files). A `.res` produced on any machine links with `{$R x.res}` and loads on Delphi 12 CE, FPC/Windows and FPC/Linux (all three tested). The 32-bit `.res` format is simple enough to write directly: `scripts/build_rcdata_res.py` does it on any OS, byte-for-byte identical to what `windres` produces for the equivalent `NAME RCDATA "file"` lines. Either version the generated `.res` and check it in CI (`--check`), or regenerate it in a pre-build step. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `tools/build_sql_res.py` (a tree-of-`.sql` variant used by its test suite)
- **With a unit output folder (`-FU`), FPC links a same-named `.res` from the program's folder instead of the path in `{$R}` — and the Delphi IDE writes `<Project>.res` exactly there.** Observed: a program linked its embedded SQL with `{$R 'sql/Migrations.res'}` (the program is `Migrations.dpr`); it passed on Linux FPC until the project was built in the Delphi IDE, which wrote its own `Migrations.res` (icon/version info) next to the `.dpr`; from then on every Linux run failed to find the SQL resources, and passed again with that file removed. Isolated with FPC 3.2.2 on linux and win64 (x86_64): a program with `{$R 'sub/data.res'}` and another `data.res` next to it gets the one next to it when built with `-FU`, whatever the program is called; without `-FU` it gets `sub/data.res`. No warning either way; lazbuild passes `-FU` whenever the project has a unit output directory, which new projects do. Fix: never give an embedded `.res` the project's name (or any name that may also exist next to the program), e.g. `sql/MigrationsSql.res`. Not measured: Delphi's resolution of the same case, and FPC versions other than 3.2.2. — [`pascal-db-faa`](https://github.com/fabianoallex/pascal-db-faa), `samples/03-migrations/Migrations.dpr`
